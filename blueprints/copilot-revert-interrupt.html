Copilot blueprint — Revert & Interrupt · Crusor Agent pane

Read-only frames. Every behaviour below is quoted from the shipped pipeline (src/runtime/turn_control.py, src/graphs/chat_graph.py, src/tools/shadow_checkpoints.py, src/bridge/, desktop/vscode/src/vs/workbench/contrib/crusorai/) — nothing here is implemented yet.
Two rules govern the whole document: interrupt is a hand brake — one pull, it bites where the turn stands, no wind-down and never the words “stop safely” — and undo lives on the user request row, following Copilot's own checkpoint line.

F1 · Running — the brake, armed

While a turn runs, the right-hand button is not “send”. It is the hand brake: a solid stop square in the same slot, one pull, no menu, no confirmation, no “are you sure”. Pulling it cuts the turn where it stands — the model stops being asked, the queue is dropped, nothing else is admitted. the composer still steers while you type

The brake model (what the copy must never say)

  • No “stopping”. The brake is a state transition, not a process: the turn is running, then it is interrupted.
  • No “safely”. Nothing is being protected by waiting. There is no grace window, no countdown, no “finishing the current step”.
  • No confirmation. Undo is already covered: the workspace snapshot was taken before the first write (F4), and the request row can put the tree back (F5).
  • One exception, stated as a fact afterwards: a file write that is already inside the OS call cannot be un-written — it lands, and the receipt says “1 write landed” rather than pretending it was rolled back.

F3 · Settled — the interrupted receipt

The turn ends like any other: with a receipt row. An interrupted run keeps every fact it produced (text so far, tool results, diff) and counts what the brake actually did — landed versus dropped. It never claims success, and it never deletes work.

F4 · The snapshot model that makes Undo honest

The agent does not “remember” how to undo — it snapshotted the whole workspace before the first mutation of each iteration, transparently, into a private git store the user's project never sees (~/.crusorai/checkpoints/store, refs refs/crusorai/<hash16>). One snapshot per workspace per turn; a turn that changed nothing mints no commit.

Before the first write of every iteration
  • begin_agent_turn() resets per-turn dedup at ai_node entry.
  • First write_file / edit_file / execute_code / run_terminal / scaffold calls checkpoint_before_mutation(workspace, reason) — e.g. “before write_file: src/app/page.tsx”.
  • Read-only commands skip the snapshot entirely.
shadow_checkpoints.py:695–712 · chat_graph.py:1322 · file_tools.py:407
Restore semantics (already implemented server-side)
  • Overwrite, never delete: files created after the snapshot stay on disk.
  • Undo the undo: restoring takes a pre-rollback snapshot first, so the restore itself is reversible.
  • Cross-project guard: a commit must be an ancestor of this workspace's checkpoint ref.
  • Per-file restore: restore(workspace, hash, file_path).
shadow_checkpoints.py:410–475

Why this placement is the right one here

  • It is the only anchor with one meaning. A receipt-anchored Undo has to be read as “undo the thing above/below me?”; a request-anchored one reads as “go back to before I asked this”.
  • It survives interruption. Stop lands mid-response — the assistant block is partial, but the request row is always complete and always above it (F6).
  • It is where the draft belongs. Restoring a checkpoint puts the request text back in the composer in Copilot; that is the same row, one gesture, no second control. chat.shared.contribution.ts:867
  • Zero new surface. Our pane already draws the user bubble; this adds one hairline row to it, not a panel.
chatListRenderer.ts:957 (MenuId.ChatMessageCheckpoint on the request row) · chat.css:4307–4337, 4455–4490

Vocabulary, one word per scope: Undo turn = this request's snapshot · Continue = send the same request again · Undo All Edits = the whole working set (F7) · Cancel = stop a running turn. Copilot calls the first one “Restore Checkpoint” and, on the very first request, “Start Over” — an open question below.

Open questions for you (answers change the frames)

QuestionWhy it matters
The first request in a session: Undo turn (back to the snapshot before it) or Copilot's Start Over (clears the chat and undoes everything)? Copilot swaps the label on request #1 exactly here. Our baseline snapshot for the first turn is a real, restorable state — so we either keep one word for all rows, or mirror the swap and accept two meanings on one line.
Keep the Undo turn label, or say Copilot's Restore checkpoint / Revert? The tooltip carries the meaning either way; the label is what gets scanned. “Undo turn” reads as an action on the conversation; “Restore checkpoint” reads as an action on the files.
Do we delete files created after a snapshot when the user restores? Server restore is overwrite-only today. Deleting is a bigger promise and needs its own confirmation.
Per-file ↩ in the Crusor pane, or keep file-level undo in the workbench's Changes view only? Duplicating the working-set UI in the pane risks two sources of truth; a narrow “last turn” list does not.
Timeline in the Manager (F7c) as a full panel, or a “restore earlier…” flyout off the receipt? 20 snapshots × whole-tree restores is a power tool; the pane is 420 px wide.
Do we mirror Copilot's Fork from here on the same row now, or leave the slot empty? session_fork already exists in the bridge protocol, so the row can host the pair the way Copilot does — but every added control on a 420 px row costs legibility.
