Backend requirements:
- A ThreadingHTTPServer-based app, runnable as `python server.py --host HOST --port PORT`.
- SQLite persistence. Honor SPRINTBOARD_DB when set; otherwise use tasks.db beside server.py.
- GET /api/health returns exactly {"status":"ok"}.
- GET /api/tasks returns {"tasks":[...]}, newest first.
- POST /api/tasks validates a nonblank title and priority low/medium/high, creates status todo, and returns 201 with {"task":...}.
- PATCH /api/tasks/{id} validates status todo/doing/done, returns the updated task, and returns 404 for an unknown id.
- DELETE /api/tasks/{id} returns 204 and actually deletes the row.
- GET /api/stats returns integer total/todo/doing/done counts.
- Serve index.html at / and the CSS/JS assets at /styles.css and /app.js with appropriate content types.
- Return useful JSON errors and never expose a traceback to the client.

Frontend requirements:
- A genuinely polished, responsive dashboard—not a bare test fixture.
- Strong visual hierarchy, an intentional color system, cards, responsive layout, hover/focus states, and at least one subtle animation.
- Header/brand plus API health indicator.
- Four live statistic cards for total, todo, doing, and done.
- Accessible add-task form with title and priority controls.
- All/Todo/Doing/Done filters, loading/empty/error states, task cards, status controls, and delete actions.
- Use the real REST API with fetch; no hardcoded sample tasks.
- Preserve the required DOM ids used by the acceptance suite.

README.md must explain features, architecture, data model, launch command, API routes, and verification command.
